# ADR 0003: 見出し認識チャンク分割と pypdf の採用

## ステータス

Accepted

## コンテキスト

計画書 §4 で「チャンク分割はセクション見出しを意識した分割と固定長との比較を ADR に記録する」
ことが求められている。また PDF ライブラリの選定も必要だった。

### PDF ライブラリ

- **PyMuPDF (fitz)**: 高速で機能豊富だが **AGPL-3.0** ライセンス。
  本プロジェクトは公開ポートフォリオリポジトリであり、AGPL の伝播条件を避けたい
- **pypdf**: **MIT ライセンス**。純 Python で速度は劣るが、
  outline (ブックマーク) からページ番号を取得する API が提供されている

→ **pypdf を採用**。

### チャンク分割方式

Bedrock ユーザーガイド (66MB, 5,496ページ) で実際に検証したところ、
PDF のブックマーク (outline) は "Overview > Quickstart" のような 3〜4 階層の
見出し構造を持ち、モデルごとの仕様ページなど粒度の細かい見出しも含めて
5,180 エントリ存在することを確認した。

固定長分割 (例: 1000文字ごとに機械的に切る) だけでは、見出しをまたいで
無関係な内容が1チャンクに混在し、検索精度と回答の出典精度 (どのセクションが根拠か) が
劣化する。

## 決定

**2段階の分割方式**を採用する。

1. **第一原則: セクション境界をまたがない**
   outline の開始ページから「そのページが属する最も深い見出し」を逆引きし
   (`app/ingestion/parse.py: section_for_page`)、同一セクションのページ群をまとめる
2. **セクション内: 文字数ベースのスライディングウィンドウ** (既定 1500文字 / オーバーラップ200文字)
   段落境界 (`\n\n`) → 改行 → 半角スペースの優先順で分割点を探し、
   見つからない場合のみ機械的に window 幅で切る (`app/ingestion/chunk.py: _window_split`)
3. 分割後に生じた極端に短いチャンク (100文字未満) は、同一セクション内であれば
   直前のチャンクへ吸収する

window / overlap はパラメータ化しており、固定長分割との比較実験は
`chunk_pages(pages, window=..., overlap=...)` の引数を変えて再実行することで
いつでも再現できる。

### 除外: Table of Contents

実データで検証したところ、目次ページ (`section == "Table of Contents"`) は
ページ番号の羅列 (`.......... 9`) のみで構成され、埋め込み・検索対象として
無意味かつコストの無駄になることが判明した。`app/ingestion/ingest.py` で
目次セクションのページを取り込み対象から除外している。

## 影響

- 実データ (Bedrock UG) で 5,476 ページ (目次除外後) → 6,483 チャンク、
  概算入力トークン数 約195万トークン (Cohere Embed v4)
- `--dry-run` オプションで投入前に規模を確認できる
